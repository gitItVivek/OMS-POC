Slide 2 — What we implemented

Three coexisting bench paths — all in integration-service

#ApproachBench endpointWho orchestratesEvent adapter

B Camel-heavy pipeline POST .../camel Camel DSL PlaceOrderCamelPipelineRoutes Camel (full pipeline)
C Saga + Spring Integration POST .../spring-integration Java SagaOrchestratorServiceImpl (same as A) SI OrderSagaIntegrationFlows

Domain services (order, inventory, fulfillment, notification) use plain @KafkaListener — no Camel, no Spring Integration.

A vs C: identical saga brain, saga_instances, oms.* topics. HTTP path tags event_adapter (CAMEL vs SPRING_INTEGRATION). Both listeners stay active — safe concurrent Postman runs.

B: isolated oms.camel.* topics — runs side-by-side with A or C.

PS (term meaning): thin Camel = Camel only delivers Kafka events to Java saga methods; camel-heavy = Camel DSL owns routing/branching/compensation; Spring Integration = same Java saga as A, but event adapter is Spring Integration instead of Camel.

Slide 6 — Implementation A: Saga + Kafka + thin Camel (plain English)

How approach A works — step by step

① HTTP: BenchPlaceOrderController → SagaOrchestratorService.startPlaceOrder() → saves saga_instances → SagaCommandPublisher sends first Kafka command ② Domain: order / inventory / fulfillment consume commands via @KafkaListener → do their work → publish events back to oms.* ③ Loop: OrderSagaRoutes (Camel) hears each event topic → JSON unmarshal → calls onOrderCreated(), onStockReserved(), etc. ④ Java decides every next step and publishes the next command. Camel is the receptionist only.

Camel is not the brain — ~47 lines, five identical mini-routes. No split, choice, or Kafka producer in routes.

Slide 8 — Implementation C: Saga + Kafka + Spring Integration (plain English)

How approach C works — same manager, different receptionist

① HTTP: SpringIntegrationBenchController → same startPlaceOrder() → same saga_instances → same SagaCommandPublisher → same oms.* commands ② Domain: unchanged — @KafkaListener in order / inventory / fulfillment ③ Loop: OrderSagaIntegrationFlows (Spring Integration) hears the same five event topics → JSON transform → calls the same saga bean methods as A ④ Ownership: event_adapter=SPRING_INTEGRATION on saga row → Camel OrderSagaRoutes off → no double-processing on oms.*

Only integration-service has Spring Integration. Domain microservices are untouched.

Slide 16 — How to read the numbers

Interpretation checklist

  • All three: 0% errors at 10 users / 200 orders — no reliability difference at this load.
  • B (Camel-heavy) is not faster — do not choose it for performance.
  • A vs C — adapter swap only; POST 18 ms vs 28 ms mean on different run dates — pick by team skills, not this POC gap.
  • Runs on different dates (A/B 7 Jul, C 8 Aug) — not a certified lab comparison.
  • Use latency & completion time for comparison, not throughput from mixed test plans.
  • Core recommendation unchanged: saga-style Java orchestration + thin messaging layer.

Slide 17 — Recommendation

What we recommend for OMS-POC

Keep saga orchestration in Java. Use a thin messaging adapter for Kafka events.

All three paths coexist for benchmarking. A and C share the Java saga brain — pick Camel or Spring Integration as the Kafka adapter. B is a separate Camel-heavy style on oms.camel.*; more complex, no speed win in Jul 2026 runs.

Slide 25 — Search interest: how it works & files

Implementation walkthrough (plain English)

Step-by-step — what happens

  1. User searches GET /api/search?q=chair on order-service
  2. Order calls inventory over HTTP for FTS/fuzzy catalog results
  3. Query normalized to interest_key (e.g. "chair") — dedup per user
  4. If new interest → save row in search_interests + bump trends
  5. Spring event → SearchInterestEventListener publishes Kafka event
  6. Camel route consumes → checks rate limit (max 2 emails / 72h)
  7. If allowed → fetch email from identity → Kafka notify command
  8. notification-service logs stub "email" to notification_log

Camel components used (this flow)

ComponentRole
Kafka consumerListen oms.search.interest.registered.event
unmarshal JSON→ SearchInterestRegisteredEvent
beanevaluateRateLimit, buildNotificationCommand
choice / whenSend email OR skip if rate limited
Kafka produceroms.notification.send.command

This is where Camel shines — content-based routing — without needing a full saga.
